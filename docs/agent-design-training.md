# 壓縮大師如何設計與訓練

[回作品首頁](../README.md)

Author: Nio (Master) · Evidence review and editing: Codex · 2026-10-17

## 背景與研究目標

長文縮短之後，字數達標不代表資訊完整。Nio 最初要求建立可重用的壓縮 agent 與配套流程，以十篇腸腦軸文獻試跑，要求縮短 35%（保留原文 65% 字元），經 Claude 提案後確認 ±3 個百分點容差；由兩位 reviewer 對照全文與稿件，記錄每篇修訂次數。

目標分成兩層：任務層要求稿件縮短且保留精髓；方法層研究如何從失敗修訂 agent 的規則。此處訓練不涉及模型權重更新，也不表示模型會自動記住前次錯誤；教訓必須寫進後續會載入的角色設定。

## 設計依據與取捨

本案例的直接依據是角色設定、試跑與審查紀錄，沒有用外部論文替本方法背書。

| 設計 | 要處理的問題 | 取捨與限制 |
|---|---|---|
| Writer 與 reviewer 分工 | 寫得短與判斷失真需要不同檢查視角 | 多角色增加呼叫成本；尚未證明雙審優於單審 |
| 事實與論證分開審 | 數字正確仍可能失去定義；句子通順仍可能斷掉論證 | 兩者在條件、否定與因果上有重疊，不是完全互斥分類 |
| Reviewer 不互讀，也不收 writer 自評 | 避免直接受其他角色的結論引導 | 只是輸入隔離，共享模型與判準仍可能有共同盲點 |
| 任一 revise 即退回 | 不用多數票忽略一個已提出的失真問題 | Reviewer 也可能誤判；需要回原文判斷，不把意見自動當真 |
| 規則附失敗來源 | 知道為什麼有這條規則、未來要驗證什麼 | 附來源只建立可追查性，不能證明規則有效 |

## 材料與訓練方法

1. **定義驗收**：分開量測字元比例與內容品質；空白、標點納入字元數。歷史配置為 Sonnet writer、Haiku 事實 reviewer、Sonnet 論證 reviewer。
2. **建立角色契約**：writer 收原文、目標比例、輪次及前輪 issues；reviewer 收原文與當輪稿件，回傳判斷、問題位置、失真類型及修改方向。
3. **試跑與修稿**：兩位 reviewer 分開審查，再合併 issues 交回 writer。設計上最多五輪，未解問題必須保留；歷史執行曾偏離同版重審規則，見下文。
4. **回看錯誤**：區分漏事實、失去量化判據、斷裂論證、過度確定措辭與格式殘留。
5. **修訂 agent**：把失敗轉成具體規則，標記來源；保存 v1 作為後續比較基礎。
6. **提出再驗證**：用固定條件比較版本與個別規則。這是後續研究設計，不能寫成已完成的增益證據。

### 案例一：修復論證引入新失真

以下是現存歷史 review log 的摘要，沒有完整逐輪稿件快照可獨立重播當年的每一次判斷。

| 位置 | 審查觀察 | 後續處置／規則 |
|---|---|---|
| Paper 01，iter 1，S2 | 壓縮稿弱化兩種實驗條件下的效果對比 | 要求補回對比；v2 G3 要求保留條件兩側 |
| Paper 01，iter 2，H5/H6 | 補寫後新增強調語氣或過度確定的連接語 | 下一稿刪除強調、降低措辭強度；G2 明列禁止新增此類語氣 |
| Paper 01，iter 3 | 歷史紀錄列兩位 reviewer 通過 | 只能說當時紀錄通過，不能推論所有失真均已排除 |

這一例的價值是呈現**修稿會產生新錯誤**，因此 reviewer 需要再看修改後的稿件。它也說明不能直接照抄 reviewer 的建議：回饋仍須受原文限制。

### 案例二：留下數字，卻失去數字的意義

Paper 02，iter 1，H1 記錄：稿件保留 IC50 濃度，卻省略它對應的 50% 抑制判據。v2 G4 因而明定保留量化數值時，也保留判據意義。

但該篇 iter 2 沿用了前輪論證 reviewer 的 pass，並未完成同版雙審；現存稿件字元數也與當時最終紀錄不同。本案例能展示規則來源，不能當成嚴格驗收成功的證據。詳見 [歷史核對資料](historical-audit.json) 的第二筆。

## v1 → v2：改的是什麼？

| 項目 | v1 | v2 的設計 |
|---|---|---|
| 工作步驟 | 讀取、規劃、改寫、寫出與回報 | Plan → Execute → Audit → Emit，明列各階段任務 |
| 行為規則 | 同層列出保留、刪減與修訂要求 | Core Principles、G1–G8 失敗防範規則、機械檢查分層 |
| 篇幅分配 | 依內容規劃壓縮 | 明列各論文章節的不同削減建議，再對齊總字元比例 |
| 回報 | 字元比例與修訂說明 | 增加計畫摘要、刪減摘要、不確定處與檢查結果 |
| 後續比較 | 保留歷史版本 | 規則附案例來源，便於設計移除單一規則的對照 |

Plan 在原始設定中仍主要是 agent 內部規劃，只要求交付摘要，並非完整可重播的決策軌跡。設定中的「token budget」實際以字元比例操作，不能宣稱已量測 token 預算。

規則來源也不是全部一樣完整：G4 可對到 Paper 02 的 H1；G8 的來源仍寫成籠統的 Sx/general。v2 還同時存在「篇幅超界就修正」與「必要時可略超界以保精髓」的優先序問題。這些都應視為角色設計的待釐清點，而非完善的通用規範。

## 結果與討論

歷史十篇資料留下壓縮稿與審查紀錄，支援「已試跑並從錯誤形成規則」的敘述；其中第一篇記錄三輪、第二篇記錄兩輪。然而部分稿件字數與紀錄不符，且存在沿用舊 verdict，不能沿用早期彙總的嚴格 100% 通過主張。

2026-10-08 另將既有角色規準交給 Codex agents，在一篇工程文章上完成一輪壓縮與雙審查。這次沒有 reviewer 退回修稿，支持的是方法移植可執行，不是修訂迴圈的品質增益。詳見 [實測報告](experiments/2026-10-08-openai-harness.md)。

沒有 v1/v2 固定條件比較、單審/雙審對照與人工金標準，尚不能宣稱哪一條規則造成成效提升。Nio 在當時對話要求可量化、可重複的實證，並將壓縮視為 lab 的子項目；這是本作品方法設計的重點。

## 與目前 Python 程式的關係

- [core.py](../runtime/core.py) 保存原文與每輪稿件、核對 reviewer 回應的來源/稿件指紋、控制修訂與停止。它沒有自動從 issues 更新 agent 設定。
- [claude_adapter.py](../runtime/claude_adapter.py) 從本機載入既有角色檔，調整為 JSON 輸入輸出；它需要外部角色檔，不是 repo 內自足的 v2 訓練包。
- [http_adapter.py](../runtime/http_adapter.py) 使用程式內的精簡角色提示，不能當作完整 v2 提示詞的等價版本。
- Codex 單篇實測透過主線派工與 [handoff_adapter.py](../runtime/handoff_adapter.py) 交接，角色快照與指紋的額外核對見該實測報告。
